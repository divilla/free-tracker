## 1. Brief

Provide a script-owned, durable and fail-closed **preparation** boundary for one planned change: validate identity/prerequisites, select an exact baseline, create an isolated worktree without disturbing user work, serialize ownership and reconcile interrupted preparation. Successful preparation is not successful implementation, review, merge or product validation. S004 consumes this boundary and owns the later execution loop.

The clean authoring baseline contains S001 app/tests and S002 setup/checker/tests. S002 reports earlier passing checks, followed by F01/F02 tooling passes but failed full `make unit-test` at the read-only Flutter SDK cache and failed remote verification. Those scoped historical results remain historical. Git source presence and the local squash-looking commit do not prove independent review or the verified merge procedure. The publisher's authoring clarification resolves the stale PLAN baseline, not those gates.

## 2. Scope

- **In:** bounded preparation/status/resume CLI; explicit baseline configuration and prerequisite checks; exact PLAN/change identity; durable versioned per-change records and safe portable snapshots; isolated worktree creation; repository-wide per-change locking across linked worktrees; interruption/fault reconciliation; usage/bootstrap documentation and mapped infrastructure tests.
- **Out:** model invocation, authoring automation, implementation dispatch, check execution/commit/review/fix loops, retry policy for those loops, actual integration/conflict resolution, squash/push/PR creation, promotion, cleanup of user branches/worktrees, app/UI/measurement/storage changes and GW completion. S004 owns those execution behaviors; S005 owns extending real SQLite/app test foundations.
- **Integration:** S003 owns the preparation entry point and shared state/lock primitives under `scripts/`, plus runtime/portable record consistency. Reuse Perl and existing Git fixture conventions; introduce only the preparation entry point/shared primitives missing from the inspected helpers. S004 is the next consumer and must reuse the identity, baseline, evidence invalidation and ownership contract rather than create a second competing ledger. Its target-wide merge lock is separate from S003's per-change ownership lock.
- **Risks/prerequisites:** Git common-dir resolution in linked worktrees; interruption between Git and file writes; stale remote refs; record files themselves making a worktree dirty; lock lifetime; malformed/unsupported or legacy artifacts; host/tool permissions. Required local tools are Git, Perl with core JSON/file/locking support, Bash for existing regression suites and Python 3 for existing tooling checks. No Codex, network account or Android device is required to test this preparation boundary with local remotes. Production remote access still needs the configured authentication and successful refresh.

## 4. Contracts

### Reference architecture and integration ownership

This is repository tooling, not an application feature. Leave S001's `lib/app/composition.dart`, `lib/settings/application/app_info_loader.dart`, `lib/settings/domain/app_info.dart` and `lib/settings/data/platform_app_info_repository.dart` unchanged. No Flutter/SQLite/sensor dependency is introduced into plain-Dart rules; the app's single recording owner is unaffected. Shared workflow primitives belong under `scripts/lib/mch/`, separate from terminal-only `Progress.pm`. Extend existing temporary Git fixture helpers where suitable; never run tests against the user's remote or real Codex.

S003 implementation documents the audit/dispositions above in `scripts/README.md`, including exact commands, prerequisites, artifact locations, local-versus-remote behavior, status/exit semantics, unsupported legacy resume and safe recovery. Necessary PLAN/IMPLEMENT reference reconciliation must preserve their gates. Do not remove/relocate maintained helpers. Existing legacy entry points are not silently relabeled as conformant; S004 must integrate later phases before unattended use.

### Preparation CLI

The following **planned, not currently implemented** interface is the S004 handoff:

```text
perl scripts/workflow-run.pl start <slug> --worktree <new-path> --remote <name>
perl scripts/workflow-run.pl start <slug> --worktree <new-path> --local
perl scripts/workflow-run.pl status --run <run-id>
perl scripts/workflow-run.pl preflight --run <run-id>
perl scripts/workflow-run.pl resume --run <run-id>
```

Resolve the repository from the script location/Git common directory, not the caller's working directory; persist a canonical repository identity. Exactly one of `--remote <name>` and `--local` is required on start. Local mode explicitly uses `refs/heads/dev`, records remote freshness **not checked**, and is not a workaround for a failed configured remote refresh. Remote mode validates the named configured remote, authenticates without copying credentials into records and fetches `refs/heads/dev` using an explicit refspec (including restricted-fetch clones). Select the refreshed commit, record observation/command/exit, then resolve it as a commit. No automatic `dev`/`stage`/`master` initialization or remote writes. Remote URL credentials must not appear in diagnostics or portable records; persist the remote name, not a credential-bearing URL.

The branch regex is `^change/([0-9][0-9][0-9]+-[a-z0-9-_]+)$`; the captured numbered slug is unchanged. Match the complete slug, numeric ID and `agent/changes/<slug>.md` resolved from the PLAN row. Start requires the authored readable selected change, unlike the legacy flow's author-before-implementation behavior. Missing/unreadable governing files, duplicate/mismatched inventory rows or unresolved authoring placeholders block. Dependencies come from the matched row and their transitive prerequisites. Verify the consuming contract's required source/evidence, not only ledger labels: require a scoped evidence reference, revision/content identity and result for executable prerequisites, or a recorded explicit publisher exception limited to the consuming gate. Unverified physical/account facts assigned to later changes remain visible, not falsely required for unrelated preparation. In particular, the S003 authoring exception above is not general implementation readiness.

Start checks the complete caller repository status (including hidden untracked files and dirty submodules regardless of user Git ignore-status configuration) before authentication/remote access. It also checks the worktree destination does not exist, branch/run ownership is absent and target refs can be resolved. Recheck after refresh/before creation under the ownership lock. Create the branch/worktree using ordinary non-forcing Git operations at the recorded baseline; do not switch the caller checkout. Preserve unrelated ignored files, and never stage them. An existing branch, remote-tracking change branch, runtime record or destination is not fresh work: reject and direct the operator to an existing run or manual reconciliation. Never infer legacy-run completion or manufacture its record.

`status` is read-only and prints validated recorded state plus available Git observations, identifying an active writer and any pending reconciliation; it does not refresh, repair or acquire a mutating gate. A valid inspection may exit 0 even when reporting a blocked phase; its output must say `run_complete: false`. Malformed/missing state fails nonzero. `preflight` rechecks prerequisites/configuration/refs under the mutation lock and records observations without launching later phases. `resume` performs the same checks and reconciles only preparation. Neither restarts implementation/review/merge. Unsupported later phases report that S004's consumer is required, never a prepared/merged success.

Mutating phase commands return 0 only for their successfully completed named phase; invalid usage returns 2, other unmet gates/failures return nonzero (1 by default). SIGINT/SIGTERM return 130/143 after stopping active child work and best-effort durable interruption recording. JSON output includes run ID, slug, phase, phase result, `run_complete: false`, baseline/source, blockers, next action and runtime/portable paths; diagnostics go to stderr. A successful status/read is never approval to advance a workflow gate.

### State, paths and compatibility

**Reconciliation decision grounded in the audit:** preserve `codex-plan-runs/*.tsv` and `codex-plan-run.lock` in their existing Git-metadata locations. They remain plan-dispatch artifacts. Operational per-change state must also survive branch switches and cannot live only in an untracked branch-dependent file. Use the canonical `git rev-parse --git-common-dir` directory for private runtime records/locks; publish a sanitized machine-readable snapshot under `agent/progress/` to satisfy PLAN §8. This is one authoritative runtime record plus a portable projection, not two independently advancing gate ledgers.

| Record | Planned location / contract |
| --- | --- |
| Runtime record | Git common directory: `codex-workflow-runs/<run-id>/state.json`; private permissions; authoritative for local preparation/resume |
| Owned evidence | Same run directory, outside automatic staging; record artifact relative paths/integrity identifiers, not raw payloads in PLAN |
| Per-change lock | Git common directory: `codex-workflow-locks/<slug>.lock`; stable lock inode, nonblocking exclusive OS lock; owner diagnostic contains run ID/host/process |
| Portable projection | Prepared worktree: `agent/progress/runs/<run-id>.json`; safe versioned snapshot with runtime generation and content identity; no absolute host paths, raw command output, remote URL or secrets |
| Existing plan dispatch | Existing per-worktree Git `codex-plan-runs/` TSV and common `codex-plan-run.lock`; never imported as a clean check/review/merge |

Use an opaque unique run ID restricted to safe filename characters; reject traversal/separators, unsafe symlink destinations and paths escaping owned directories. New record creation is exclusive. Canonical repository/common-dir and worktree identities are runtime-only; portable worktree location is a relative reference or explicitly local/unavailable marker, not a fabricated relocatable path. Only the exact run-owned projection is expected bookkeeping dirt; it is not permission to ignore all of `agent/progress/`. Unrelated pre-existing files there remain protected. S003 never stages or commits even its own projection; S004 owns explicit safe selection and final portable/PLAN publication. A new start may therefore leave the prepared worktree with that one uncommitted bookkeeping file, which status/preflight recognize by exact path/content/generation.

Schema version **1** requires these semantic fields (representation details must be documented/tested in implementation, not left to agent prose):

- Run ID, change ID, exact slug/branch/change path, repository/worktree identity, schema version and monotonically increasing record generation.
- Configuration snapshot: explicit local/remote mode, remote name when applicable, target `dev`, selected worktree and effective prerequisite/evidence references; identity/configuration cannot silently change on resume.
- Original baseline, observed latest target, observed source HEAD and preparation-intent commit, all full object IDs validated in the actual repository. Original baseline is immutable; observed target/source changes do not rewrite history.
- Current phase, previous/resume phase, phase result, blockers with reason/owner/next action, UTC observation/update timestamps and next action. Sequence/generation orders transitions; wall-clock timestamps are not lock leases or evidence freshness guarantees.
- Check and review containers initially empty; merge commit initially null; implementation/review/merge/requirement-validation gates unset/unmet and entire-run completion false. S004 defines the later evidence-entry/findings schemas and phase transitions before producing them. Preserve supported extension fields; reject unsupported schema versions/phase transitions without dropping data or accepting approval.
- Artifact references and projection generation/content digest; references are not proof the referenced evidence passed. The runtime record stores SHA-256 of the exact published projection bytes. The projection carries run ID, generation and sanitized source identity, not a reciprocal hash of the full runtime record; avoid self-referential hashes. Preserve previous committed state on failed writes and keep failure diagnostics outside the corrupt/partial target.

S003 phases are `preparing`, `prepared`, `blocked` and `interrupted`. Blocked/interrupted records retain the last durable phase and recovery action. Acquire the per-change lock before creating/mutating a run or refreshing refs. Validate configuration/dirty inputs first where read-only validation is possible. Persist preparation intent **before** branch/worktree creation; verify resulting branch/worktree/HEAD; publish the portable snapshot atomically; only then acknowledge `prepared`. Do not label a run `merged`, product-validated or complete in S003. Do not allocate fictitious checks/review rounds.

Use same-directory temporary files, checked writes/flush, file synchronization, atomic rename and directory synchronization for durable replacements on the supported host filesystem. Fail explicitly if required durability cannot be established. Serialize writers under the common-dir lock and compare generation before replacement so an obsolete read cannot overwrite a newer record. Keep the last committed valid record through pre-rename failure. Runtime/projection writes are not one filesystem transaction: record intent/generation and reconcile a crash between them; a stale/missing projection cannot authorize success. Update only owned records, never sanitize arbitrary user files in place.

### Ownership, resume and next consumer

Use the same OS lock for start/preflight/resume across linked worktrees; PID/age metadata alone is not ownership. Hold it through active Git children and durable writes; do not release while a surviving child could mutate the run. A contender returns nonzero without replacing the first owner's record. Do not unlink an active lock file or use timeout-based lock stealing. When the kernel releases a dead owner's lock, resume first reconciles actual Git, even if metadata still says active. Keep the existing outer plan lock separate so a future plan dispatcher can own it while a child owns its per-change lock. S004 owns target-wide merge serialization and deadlock-free lock ordering before any merge is enabled.

Resume validates actual branch and worktree registration/path, original baseline existence, observed source, fresh target (in remote mode), clean/recognized bookkeeping state and immutable configuration. If the recorded creation intent matches a branch/worktree already created by this run, adopt that verified outcome **within the same run** and finish projection/bookkeeping; do not create duplicates. If creation did not happen, retry only the recorded non-forcing creation step. An unexpected branch at a different commit, different owner/path, missing/moved user worktree, ambiguous partial Git result or dirty unrelated files blocks with preserved evidence and manual recovery instructions; no destructive rollback/cleanup.

A changed source or target is an observation requiring revalidation, not a new trusted baseline or continued approval. Preserve original baseline and prior evidence, mark any source/target-bound evidence unusable and block pending S004's integration/check/review handling. S003 cannot resolve conflicts or declare stale evidence fresh. Even when the observed tree contents match, a different bound commit is not silently accepted. A record containing merge evidence/later phases is not proof a new merge is needed: S003 never merges, and routes that recovery to S004. Missing/corrupt/unsupported state or legacy TSV alone requires explicit operator reconciliation, never `start` over an existing branch.

No app persistence, serialization, migration, tour-time, unit or sensor contract changes are introduced. JSON workflow persistence is tested with real filesystem/Git faults; it is not an SQLite implementation or a substitute for S005/S009 database tests.
